특정 업무단 화면에서 예외가 발생했다.

```
org.springframework.jdbc.UncategorizedSQLException: SqlMapClient operation;
uncategorized SQLException for SQL []; SQL state [63000]; error code [3150];
--- Check the testDAO.selectTest-InlineParameterMap.
--- Cause: java.sql.SQLException: ORA-03150: 데이터베이스 링크를 위한 통신 채널의 파일 끝
ORA-02063: line가 선행됨 (DB_LINK_1 부터)
```

늘 하던 대로 스택트레이스를 위에서부터 훑었다. 그런데 여러번 다시봐도 **고칠 부분이 안 보였다.**

쿼리도 멀쩡했다.

```sql
/* testDAO.selectTest */
SELECT TEST_COL 
FROM TABLE1@DB_LINK_1
WHERE TEST_ID = ?
```

아무런 문제가 없었다. 게다가 다시 호출하면 성공했다. 같은 코드, 같은 파라미터, 같은 쿼리인데도 불구하고 한 번 터지고 그 다음엔 멀쩡했다.

이런 적이 가끔가다 있었다. 하지만 이번엔 잡아내고 싶었다.

## 정직한 스택트레이스
`ORA-02063: line가 선행됨 (DB_LINK_1 부터)`. **이 에러가 원격 DB 쪽에서 왔다**는 의미다.

회사 프로젝트에 연결된 로컬 DB는 일부 데이터를 자기가 갖고 있지 않다. `@DB_LINK_1` 라는 DB 링크를 통해 다른 DB에서 조회한다.

그러니 이 예외의 발생지점은 WAS와 로컬 DB 사이가 아니다. **로컬 DB와 원격 DB 사이**다. WAS는 로컬 DB에 SQL 하나를 요청했을 뿐이고, 그 SQL 안에 `@DB_LINK_1`가 있어서 로컬 DB가 알아서 원격으로 나갔다가 실패한 것이다.

애플리케이션 코드에 고칠 곳이 없었던 이유가 여기 있었다. 

## 커넥션에 연결된 링크
그럼 왜 하필 그 순간 실패했고, 왜 재시도하면 성공하는가. 원인은 DB 링크 세션의 생명주기에 있었다.

1. WAS가 커넥션 풀에서 로컬 DB 세션을 하나 빌린다.
2. 그 세션이 `@DB_LINK_1` 쿼리를 실행하면, **로컬 DB가 그 세션 전용으로 원격에 연결(DB 링크 세션)을 하나 연다.** 이건 WAS도 DBCP도 모르는 연결이다.
3. 쿼리가 끝나고 커넥션이 풀에 반납돼도 로컬 세션 자체는 죽지 않는다.(재사용해야 하니까) **거기에 사용된 DB 링크도 닫히지 않는다.**
4. 그 링크가 한동안 안 쓰이면, 중간 방화벽이나 원격 DB가 유휴 연결로 판단해 끊는다.
5. **로컬 DB는 끊긴 걸 통보받지 못한다.** 그래서 다음에 그 링크로 쿼리를 보내다가 그제서야 ORA-03150을 낸다.
6. 실패하면서 로컬 DB가 죽은 링크를 폐기하고, 다음 호출은 새 링크를 연다. 그래서 재시도가 성공한다.

커넥션 풀이 하는 일은 로컬 세션을 죽이지 않고 오래 재사용하는 것이지만 그 장점이 그대로 **DB 링크를 오래 방치되게 만드는 조건**이 된다. 풀이 없어서 요청마다 세션을 열고 닫았다면 세션이 닫힐 때 링크도 같이 정리됐을 것이다.

## 풀 설정

```java
ds.setMaxTotal(50);
ds.setMaxIdle(30);
ds.setMinIdle(15);
ds.setMaxWaitMillis(10000);
ds.setRemoveAbandonedOnBorrow(true);
ds.setRemoveAbandonedTimeout(300);
ds.setLogAbandoned(true); // 로컬 전용
```

이게 전부였다. 4년을 쓰면서 한 번도 의심하지도, 관심가지지도 않은 설정들이다.

하지만 이번에 알아보는 김에 더 자세히 알아보다가, 여기엔 없는 다른 설정들도 알게 되었다.

- `initialSize` 없음 → 기본값 0. 서버가 커넥션 0개로 시작한다.
- `validationQuery` / `testOnBorrow` 없음 → 죽은 커넥션인지 확인하지 않고 그냥 빌려준다.
- `timeBetweenEvictionRunsMillis` 없음 → **유휴 커넥션을 주기적으로 점검하는 Evictor 스레드가 아예 뜨지 않는다.**

Evictor는 커넥션 풀의 백그라운드 청소부 같은 존재다. 일정 주기마다 놀고 있는(idle) 커넥션을 검사해 죽은 커넥션을 제거하고, 필요한 경우 `minIdle` 개수도 유지해 준다.

Evictor가 안 돌면 `minEvictableIdleTimeMillis`도 `testWhileIdle`도 `minIdle` 도 전부 의미없는 설정이 되므로, 회사 프로젝트의 DBCP 풀은 **유휴 커넥션을 주기적으로 점검하거나 정리하는 메커니즘이 아예 없었던 셈이다.**

결국 DB 서버가 이미 끊어 버린 커넥션도 풀 안에 그대로 남아 있을 수 있었고, 애플리케이션이 그 커넥션을 다시 빌려 사용하는 순간에야 비로소 문제가 드러날 수 있는 구조였다.

## 진짜 헷갈렸던 것들
설정 항목의 의미부터 다시 잡아야 했다. 이름만 보고 넘겨짚고 있던 게 여러 개였다.

| 설정 | 내가 믿던 것 | 실제                                                         |
| :--- | :--- |:-----------------------------------------------------------|
| `maxIdle(30)` | 놀고 있을 커넥션 목표치 | **천장.** 반납이 몰려 idle이 30을 넘을 때 초과분을 자를 뿐, 채우는 것과 무관         |
| `minIdle(15)` | 서버 뜰 때 만들 개수 | **바닥.** idle이 15 밑으로 내려갈 때만 채운다. 기동 시 생성은 `initialSize` 소관 |
| `maxWaitMillis` | 유휴 커넥션을 정리할 시간 | 풀이 꽉 찼을 때 **새 요청이 자리를 기다리는** 시간. 정리와 무관                    |
| `removeAbandonedTimeout` | 오래 걸리는 쿼리를 끊는 시간 | `close()`를 빼먹어 **샌 커넥션**을 회수하는 기준. 정상 쿼리를 잘못 회수할 수 있다      |

특히 앞의 두 개를 뒤집어 알고 있었다. minIdle/maxIdle은 오직 idle 쪽 개수만 규제하고, 최대, 최소 커넥션 수 는 이 둘과 아무 상관이 없다.

`removeAbandonedTimeout`은 판단 시간이 **빌려간 시점부터** 흐른다. 만약 정상적인 쿼리가 300초를 넘기면 멀쩡히 일하는 커넥션을 "샜다"고 판정해 뺏는다. 

> `abandonedUsageTracking(true)` 설정 시 statement 실행마다 판단 시간이 리셋돼서 이 오판을 막는다.

## 설정 변경
방향을 **커넥션을 방화벽이 링크를 죽이기 전에 먼저 갈아치우는** 쪽으로 잡았다. 커넥션이 폐기되면 거기 매달린 DB 링크도 같이 정리되고, 새로 만들어진 커넥션은 링크가 없는 상태로 시작한다.

```java
ds.setInitialSize(15);

ds.setValidationQuery("SELECT 1 FROM DUAL");
ds.setValidationQueryTimeout(3);
ds.setTestOnBorrow(true);
ds.setTestWhileIdle(true);

ds.setTimeBetweenEvictionRunsMillis(5 * 60 * 1000L);
ds.setNumTestsPerEvictionRun(-1);
ds.setMinEvictableIdleTimeMillis(10 * 60 * 1000L);

ds.setAbandonedUsageTracking(true);
ds.setRemoveAbandonedOnMaintenance(true);
```

설정은 이렇게 했지만 실제로 그렇게 도는지는 별개 문제다. 로컬에 띄우고 로그를 봤다.

### 1. 어플리케이션 시작 시점에는 아무것도 만들지 않는다
`initialSize(15)`를 줬는데 어플리케이션 시작 로그에는 커넥션이 없었다. 첫 DB 요청이 들어오는 순간 하나가 만들어지고 바로 닫히고, 15개가 한꺼번에 열렸다.

`initialSize`는 "서버 프로세스가 뜨는 시점"이 아니라 "데이터소스가 처음 초기화되는 시점"에 동작하고, 그 시점이 첫 커넥션 요청이다. 기동 직후 첫 화면이 느리고 로그가 유난히 길게 찍히던 현상의 원인이 이거였다.

하나가 만들어지고 바로 닫히는 이유는 DBCP2가 풀을 채우기 전에 `validateConnectionFactory()`로 커넥션 하나를 만들어 검증 쿼리를 실행해보고 곧바로 close 하기 때문이다.

이유는 **fail fast**, 드라이버/URL/계정으로 접속이 되는지, 그리고 `validationQuery`가 실제로 실행되는지를 첫 요청 시점에 확인해서, 잘못됐으면 데이터소스 생성 자체를 실패시킨다.

> 그래서 첫 요청 시점에 커넥션이 16번까지 열린다.(16개가 아닌 16번)

`testOnBorrow`로 인해 본 쿼리 직전에 같은 커넥션 번호로 검증 쿼리가 나간다.

 **이 검증은 로컬 커넥션이 살아있는지만 확인한다.** `DUAL`은 원격까지 나가지 않으므로, 그 뒤에 매달린 DB 링크의 생사는 검증하지 못한다.

### 3. 가만히 둬도 15개 그대로
 evictor를 5분 주기로, 유휴 폐기를 10분으로 걸어놨으니 아무 요청도 없으면 커넥션이 줄어야 한다. 컨트롤러에서 풀 상태를 찍고 한 시간 동안 방치했다.

```
active=0, idle=15    (서버 기동 직후)
active=0, idle=15    (한 시간 뒤)
```

변화가 없었다. 그래서 **minIdle(15)이 하한이니까, 지우면 15 밑으로 떨어지는 커넥션은 evictor가 폐기하지 않는** 구조로 생각했었다.
- minIdle로 유지되는 코어 15개는 회전하지 않는다.
- 그 15개가 물고 있는 DB 링크는 풀 설정으로 절대 못 지킨다.
- DB 레벨 keepalive가 없으면 답이 없다.

하지만 로그는 **내가 틀렸다고 말하고 있었다.**

### 4. 확인
더 정확하게 보기 위해 로컬에서 서버를 한 시간 반 동안 켜두고, 풀 상태를 전체 집계했더니 커넥션이 **149개 열리고 149개 닫혔다.**

```
11:29:22.086~.097   2~15번 closed   (14개)
11:29:22.170~23.086 17~30번 opened  (14개)
11:34:23.105        16번 closed     (1개)
11:34:23.185        31번 opened     (1개)
11:39:23.204~.212   17~30번 closed  (14개)
11:39:23.285~24.205 32~45번 opened  (14개)
```

5분마다 evictor가 돌고, 커넥션은 정확히 10분을 살고 교체된다. 이게 한 시간 반 동안 한 번도 어긋나지 않고 반복됐다.

**minIdle**로 인해 15개로 고정돼 있고, 그 15개는 10분마다 전부 바뀐다. 컨트롤러에서 `getNumIdle()`만 찍어서는 절대 보이지 않는 일이다. 폐기와 신규생성이 같은 evictor 실행 안에서 끝나기 때문에, 어느 시점에 찍어도 15가 나온다.

생각이 틀린 지점은 commons-pool2의 폐기 기준에 있었다.

| 설정 | 조건 | minIdle  |
| :--- | :--- |:---------|
| `softMinEvictableIdleTimeMillis` | 유휴 시간 초과 **그리고** idle > minIdle | 조건에 포함된다 |
| `minEvictableIdleTimeMillis` | 유휴 시간 초과 | **무시한다** |

내가 설정한 건 아래쪽인데, 이건 현재 idle이 몇 개든 시간만 넘기면 폐기한다. minIdle 조건을 뚫고 15개를 다 지우고, 그 직후 `ensureMinIdle`이 15개를 새로 채운다. 하나 지울 때마다 하나 채우는 게 아니라, 폐기 패스를 끝낸 뒤 부족분을 일괄 보충한다. 

> 로그에서 close 14개가 먼저 실행되고 70ms 뒤에 open 14개가 이어지는 순서가 이 이유였다.

`softMinEvictableIdleTimeMillis`는 기본값이 -1이라 애초에 돌지 않는다. minIdle을 조건으로 잡는 쪽은 꺼져 있었고, 무시하는 쪽만 켜져 있었다.

### 14와 1로 갈리는 이유
로그에는 생각이 더 필요한 지점이 하나 더 있었다. 15개가 한 번에 움직이지 않고 14개와 1개로 나뉘어 5분씩 엇갈려 돈다.

로그 맨 앞에 정답이 있었다. 11:24:20에 실제 요청이 하나 들어왔고, 그게 16번 커넥션을 썼다. 빌렸다 반납하면 그 커넥션의 **유휴 시점이 반납 시점으로 리셋된다.** 나머지 14개는 서버 시작 이후 계속 놀고 있었으니 시점이 그대로다.

> 첫 DB 요청이 들어오는 순간 하나가 만들어지고 바로 닫히니 풀에 든 건 2 ~ 16번 15개다.

그래서 14개는 11:29에, 16번은 5분 늦은 11:34에 10분을 채운다. 그리고 그 시점이 그대로 이어져, 11:29에 태어난 14개는 11:39에, 11:34에 태어난 1개는 11:44에. 요청 한 번이 만든 5분의 시차가 한 시간 반 동안 유지됐다.

## 동일한 에러가 뜰까
15개도 10분마다 교체되므로, **거기에 연결된 DB 링크도 10분마다 정리된다.** 방화벽 유휴 타임아웃이 30분이든 한 시간이든, 링크가 죽을 만큼 지연될 시간 자체가 생기지 않는다.

하지만 `minEvictableIdleTimeMillis`이 방화벽 유휴 타임아웃보다 작을 때만 방어가 적용된다. 방화벽/인프라 쪽에서 타임아웃 값을 바꾸면 프로젝트 설정은 의미가 사라진다. 

또한 유휴 시계는 커넥션이 반납될 때 리셋된다. 16번 커넥션이 요청 한 번으로 5분이 더 늘어났듯이, 커넥션이 로컬 쿼리만으로 꾸준히 사용되면 그 커넥션은 폐기 대상이 되지 않는다. 그런데 링크 쪽은 로컬 쿼리 트래픽을 받지 못하게 되므로 **세션은 바쁜데 링크만 유휴인 상태**가 만들어지고, 여기는 evictor가 손대지 않는다.

이 경우 링크는 죽고, 다음 `@DB_LINK_1` 호출에서 ORA-03150이 한 번 나고, 로컬 DB가 죽은 링크를 폐기한 뒤 다음 호출은 성공한다. 처음 내가 겪은 상황이다.

## 안 한 선택들
1. **HikariCP로 교체.**  HikariCP에는 `maxLifetime`이 있고, 공식 문서에 "인프라의 커넥션 타임아웃보다 몇 초 짧게 잡으라"고 대놓고 나와있다. 내가 설정한 evictor가 설계 기본값으로 들어가 있다. 하지만 회사 프로젝트, 폐쇄망, Spring 4.3.25 이며 무엇보다 이미 운영중인 프로젝트에 도입하는건 리스크가 너무 크다고 판단했다.
2. **validationQuery를 링크 타는 쿼리로 변경.** `SELECT 1 FROM DUAL`이 링크를 검증하지 못하니, 검증 쿼리를 `@DB_LINK_1`를 타게 만들면 링크의 연결 유무를 바로 확인할 수 있다. 하지만 이 이유 때문에 매 요청마다 링크를 여닫는 비용을 만들고 싶진 않았다.
3. **`SQLNET.EXPIRE_TIME`.** 양쪽 DB의 `sqlnet.ora`에 keepalive를 걸면 방화벽이 링크를 유휴로 판정하지 못한다. 링크를 죽였다 살리는 대신 살려두는 방식이라 위의 사각지대까지 덮고, 방화벽 값에 의존하지도 않는다. 하지만 이건 **못 한 선택이다.** DBA 업무이기도 하고 공기업 폐쇄망에서 그 절차는 짧지 않다.

> 무엇보다 DBA와 대화하려면 외부 업체와 연락해야 한다...

## 확인하지 못한 것
로컬에서 재현하고 로그로 확인한 것은 **커넥션 풀 쪽**이다. 지연 초기화, 대여 시 검증, 10분 주기 교체 등등...

**DB 링크가 방화벽에 끊기는 장면 자체는 확인하지 못했다.** 사내 폐쇄망 구성이고 원격 DB와 방화벽 정책은 내가 알 수가 없다. "10분 검사가 실제로 ORA-03150 발생률을 낮췄는가"는 운영에 올린 뒤 몇 주간 지켜봐야 안다.

## 정리
- ORA-03150의 발생 지점은 로컬 DB와 원격 DB 사이다.
- DB 링크 세션은 로컬 세션에 매달린다. 커넥션 풀이 로컬 세션을 오래 재사용하는 만큼, 링크도 오래 방치된다. 방화벽이나 원격 DB가 그 유휴 링크를 끊고, 로컬 DB는 그걸 알지 못한다.
- `minIdle`은 바닥이고 `maxIdle`은 천장이다. 둘 다 idle만 규제하며 active와 무관하다. 기동 시 생성은 `initialSize`, 대기 시간은 `maxWaitMillis`로 설정한다.
- `timeBetweenEvictionRunsMillis`가 없으면 evictor 스레드가 뜨지 않고, 유휴 폐기 / 유휴 검증 / minIdle 채움이 전부 적용되지 않는다.
- `minEvictableIdleTimeMillis`는 minIdle을 무시하고 폐기한다. minIdle을 적용하는 쪽은 `softMinEvictableIdleTimeMillis`이고 기본값은 비활성이다.
- `minEvictableIdleTimeMillis`을 설정함으로 인해 무트래픽 상태에서 idle 개수는 고정된 채 커넥션만 주기적으로 교체된다. 
- `testOnBorrow` / `testWhileIdle`의 검증 쿼리는 로컬 커넥션까지만 확인한다. DB 링크의 생사는 검증 범위 밖이다.

에러 스택트레이스에서 시작해 DBCP 설정까지 왔다. 정보를 찾아 세운 확신은 로그 앞에서 한 번 변경되었지만, 한 시간 뒤에도 15개라는 숫자만 그대로였다. 그리고 그 15개까지가 내 손이 닿는 선이었다.
