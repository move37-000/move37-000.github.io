특정 업무단 화면에서 예외가 발생했다.

```
org.springframework.jdbc.UncategorizedSQLException: SqlMapClient operation;
uncategorized SQLException for SQL []; SQL state [63000]; error code [3150];
--- Check the testDAO.selectTest-InlineParameterMap.
--- Cause: java.sql.SQLException: ORA-03150: 데이터베이스 링크를 위한 통신 채널의 파일 끝
ORA-02063: line가 선행됨 (DB_LINK_1 부터)
```

늘 하던 대로 스택트레이스를 위에서부터 훑었다. 그런데 여러번 다시봐도 **고칠 부분이 안 보였다.**

쿼리도 멀쩡했다.

```sql
/* testDAO.selectTest */
SELECT TEST_COL 
FROM TABLE1@DB_LINK_1
WHERE TEST_ID = ?
```

아무런 문제가 없었다. 게다가 다시 호출하면 성공했다. 같은 코드, 같은 파라미터, 같은 쿼리인데도 불구하고 한 번 터지고 그 다음엔 멀쩡했다.

이런적이 가끔가다 있었다. 하지만 이번엔 잡아내고 싶었다.

## 스택트레이스는 정직하게 말해주고 있었다
`ORA-02063: line가 선행됨 (DB_LINK_1 부터)`. **이 에러가 원격 DB 쪽에서 왔다**는 의미다.

회사 프로젝트에 연결된 로컬 DB는 일부 데이터를 자기가 갖고 있지 않다. `@DB_LINK_1` 라는 DB 링크를 통해 다른 DB에서 조회한다.

그러니 이 예외의 발생지점은 WAS와 로컬 DB 사이가 아니다. **로컬 DB와 원격 DB 사이**다. WAS는 로컬 DB에 SQL 하나를 요청했을 뿐이고, 그 SQL 안에 `@DB_LINK_1`가 있어서 로컬 DB가 알아서 원격으로 나갔다가 실패한 것이다.

애플리케이션 코드에 고칠 곳이 없었던 이유가 여기 있었다. 이건 애초에 애플리케이션 계층에서 벌어진 일이 아니었다.

## 링크는 커넥션에 매달린다
그럼 왜 하필 그 순간 실패했고, 왜 재시도하면 성공하는가. 원인은 DB 링크 세션의 생명주기에 있었다.

1. WAS가 커넥션 풀에서 로컬 DB 세션을 하나 빌린다.
2. 그 세션이 `@DB_LINK_1` 쿼리를 실행하면, **로컬 DB가 그 세션 전용으로 원격에 연결(DB 링크 세션)을 하나 연다.** 이건 WAS도 DBCP도 모르는 연결이다.
3. 쿼리가 끝나고 커넥션이 풀에 반납돼도 로컬 세션 자체는 죽지 않는다.(재사용해야 하니까) **거기에 사용된 DB 링크도 닫히지 않는다.**
4. 그 링크가 한동안 안 쓰이면, 중간 방화벽이나 원격 DB가 유휴 연결로 판단해 끊는다.
5. **로컬 DB는 끊긴 걸 통보받지 못한다.** 그래서 다음에 그 링크로 쿼리를 보내다가 그제서야 ORA-03150을 낸다.
6. 실패하면서 로컬 DB가 죽은 링크를 폐기하고, 다음 호출은 새 링크를 연다. 그래서 재시도가 성공한다.

여기서 커넥션 풀의 성격이 문제와 맞물린다. 풀이 하는 일은 로컬 세션을 죽이지 않고 오래 재사용하는 것이다. 그 장점이 그대로, **DB 링크를 오래 방치되게 만드는 조건**이 된다. 풀이 없어서 요청마다 세션을 열고 닫았다면 세션이 닫힐 때 링크도 같이 정리됐을 것이다.

SQL Developer로 같은 쿼리를 백 번 돌려도 이 에러를 못 보는 이유이기도 하다. 툴은 세션을 오래 붙들지 않는다.

## 그래서 풀 설정을 열어봤다

원인 방향이 커넥션 수명으로 잡혔으니 다음은 우리 풀 설정이다.

```java
ds.setMaxTotal(50);
ds.setMaxIdle(30);
ds.setMinIdle(15);
ds.setMaxWaitMillis(10000);
ds.setRemoveAbandonedOnBorrow(true);
ds.setRemoveAbandonedTimeout(300);
ds.setLogAbandoned(true);
```

이게 전부였다. 6년을 쓰면서 한 번도 의심하지 않은 설정인데, 이번에 처음으로 **여기 없는 것**이 눈에 들어왔다.

- `initialSize` 없음 → 기본값 0. 서버가 커넥션 0개로 뜬다.
- `validationQuery` / `testOnBorrow` 없음 → 죽은 커넥션인지 확인하지 않고 그냥 빌려준다.
- `timeBetweenEvictionRunsMillis` 없음 → **유휴 점검 스레드가 아예 뜨지 않는다.**

마지막 항목이 결정적이다. evictor가 안 돌면 `minEvictableIdleTimeMillis`도 `testWhileIdle`도 minIdle 되채움도 전부 잠자는 설정이 된다. 즉 이 풀은 **한번 만든 커넥션을 갱신하는 장치가 하나도 없었다.**

DB 링크를 물고 있는 커넥션이 영원히 눌러앉아 있어도 아무도 손대지 않는 구조였다.

## 진짜 헷갈렸던 것들

설정 항목의 의미부터 다시 잡아야 했다. 이름만 보고 넘겨짚고 있던 게 여러 개였다.

| 설정 | 내가 믿던 것 | 실제 |
| :--- | :--- | :--- |
| `maxIdle(30)` | 놀고 있을 커넥션 목표치 | **천장.** 반납이 몰려 idle이 30을 넘을 때 초과분을 자를 뿐, 채우는 것과 무관 |
| `minIdle(15)` | 서버 뜰 때 만들 개수 | **바닥.** idle이 15 밑으로 내려갈 때만 채운다. 기동 시 생성은 `initialSize` 소관 |
| `maxWaitMillis` | 유휴 커넥션을 정리할 시간 | 풀이 꽉 찼을 때 **새 요청이 자리를 기다리는** 시간. 정리와 무관 |
| `removeAbandonedTimeout` | 오래 걸리는 쿼리를 끊는 시간 | `close()`를 빼먹어 **샌 커넥션**을 회수하는 기준. 정상 쿼리를 오판할 수 있다 |

특히 앞의 두 개를 뒤집어 알고 있었다. active(빌려나가 쿼리 중)와 idle(풀에서 대기 중)을 구분하지 않고 뭉뚱그린 게 원인이었다. minIdle/maxIdle은 오직 idle 쪽 개수만 규제하고, active는 이 둘과 아무 상관이 없다.

`removeAbandonedTimeout`은 함정이 하나 더 있었다. 기본적으로 시계가 **빌려간 시점부터** 흐른다. 그래서 정상적인 배치 쿼리가 300초를 넘기면 멀쩡히 일하는 커넥션을 "샜다"고 판정해 뺏는다. `abandonedUsageTracking`을 켜면 statement 실행마다 시계가 리셋돼서 이 오판을 막는다.

## 설정을 바꾸고, 로그를 켰다

방향은 하나로 정리됐다. **커넥션을 방화벽이 링크를 죽이기 전에 먼저 갈아치운다.** 커넥션이 폐기되면 거기 매달린 DB 링크도 같이 정리되고, 새로 만들어진 커넥션은 링크가 없는 상태로 시작한다.

```java
ds.setInitialSize(15);

ds.setValidationQuery("SELECT 1 FROM DUAL");
ds.setValidationQueryTimeout(3);
ds.setTestOnBorrow(true);
ds.setTestWhileIdle(true);

ds.setTimeBetweenEvictionRunsMillis(5 * 60 * 1000L);
ds.setNumTestsPerEvictionRun(-1);
ds.setMinEvictableIdleTimeMillis(10 * 60 * 1000L);

ds.setAbandonedUsageTracking(true);
ds.setRemoveAbandonedOnMaintenance(true);
```

여기까지는 문서를 읽고 세운 계획이다. 실제로 그렇게 도는지는 별개 문제다. 로컬에 띄우고 로그를 봤다.

### 관측 1 — 서버가 뜰 때는 아무것도 안 만든다

`initialSize(15)`를 줬는데 기동 로그에는 커넥션이 없었다. 첫 DB 요청이 들어오는 순간 15개가 한꺼번에 열렸다.

DBCP2 데이터소스는 지연 초기화된다. `initialSize`는 "서버 프로세스가 뜨는 시점"이 아니라 "데이터소스가 처음 초기화되는 시점"에 동작하고, 그 시점이 첫 커넥션 요청이다. 기동 직후 첫 화면이 느리고 로그가 유난히 길게 찍히던 현상의 정체가 이거였다.

### 관측 2 — 대여할 때마다 DUAL이 앞에 붙는다

```
[sqlonly] org.apache.commons.dbcp2.PoolableConnection.validate(PoolableConnection.java:287)
16. SELECT 1 FROM DUAL

[sqlonly] org.apache.commons.dbcp2.DelegatingPreparedStatement.execute(...)
16. /* EduDmdExmn.getListCount */ SELECT COUNT(*) FROM SRVY_MASTER ...
```

`testOnBorrow`가 도는 모습이다. 본 쿼리 직전에 같은 커넥션 번호로 검증 쿼리가 나간다.

여기서 이 글의 결론을 미리 짚어둘 게 있다. **이 검증은 로컬 커넥션이 살아있는지만 확인한다.** `DUAL`은 원격까지 나가지 않으므로, 그 뒤에 매달린 DB 링크의 생사는 검증하지 못한다. ORA-03150을 막는 장치가 아니다.

### 관측 3 — 15개여야 할 게 30개였다

설정과 소스만 보면 커넥션은 15개에서 시작해 동시 요청만큼 늘어야 한다. 그런데 로그의 번호가 30까지 올라갔다.

원인을 찾는 데 한참 걸렸고, 답은 설정 파일 안에 있었다.

```java
@Bean(name = {"oracle19cDataSource", "19cDataSource"})
public DataSource dataSource19c() { ... dataSourceConfig(dataSource); ... }

@Bean(name = {"oracle11gDataSource", "11gDataSource"})
public DataSource dataSource11g() { ... dataSourceConfig(dataSource); ... }
```

**풀이 두 개다.** 우리 시스템은 19c와 11g 두 DB를 쓰고, `dataSourceConfig()` 공통 메서드가 양쪽에 똑같이 적용된다. 설정값 15는 풀 전체 총합이 아니라 **풀 하나당** 적용되는 값이다. 15 + 15 = 30.

로그가 이걸 감췄다. log4jdbc가 붙이는 커넥션 번호는 전역 카운터라 두 풀의 커넥션이 한 줄에 섞여 찍힌다. 로그만 보면 하나의 풀처럼 보인다.

같은 이유로, 이 번호는 커넥션의 ID가 아니다. **생성될 때마다 1씩 오르는 누적 순번**이고, 닫힌 번호는 재활용되지 않는다. 번호가 165까지 갔다고 165개가 열려 있는 게 아니다. 현재 개수는 `opened - closed`로 세야 한다.

### 관측 4 — 한 시간을 방치해도 15개 그대로

여기서 가설이 하나 생겼다. evictor를 5분 주기로, 유휴 폐기를 10분으로 걸어놨으니 아무 요청도 없으면 커넥션이 줄어야 한다. 컨트롤러에서 풀 상태를 찍고 한 시간을 방치했다.

```
19c active=0, idle=15    (서버 기동 직후)
19c active=0, idle=15    (한 시간 뒤)
```

변화가 없었다. 그래서 이렇게 결론 냈다. **minIdle(15)이 하한이니까, 지우면 15 밑으로 떨어지는 커넥션은 evictor가 폐기하지 않는구나.**

그럴듯했고, 결론까지 뻗어나갔다. minIdle로 유지되는 코어 15개는 회전하지 않는다 → 그 15개가 물고 있는 DB 링크는 풀 설정으로 절대 못 지킨다 → 결국 DB 레벨 keepalive가 없으면 답이 없다.

이 추론은 틀렸다. 그리고 틀렸다는 걸 같은 로그가 알려줬다.

### 관측 5 — 숫자는 그대로였고, 커넥션은 전부 갈렸다

풀 상태를 눈으로 본 게 아니라 로그 전체를 집계했더니 다른 그림이 나왔다. 1시간 35분 동안 커넥션이 **149개 열리고 149개 닫혔다.**

```
11:29:22.086~.097   2~15번 closed   (14개)
11:29:22.170~23.086 17~30번 opened  (14개)
11:34:23.105        16번 closed     (1개)
11:34:23.185        31번 opened     (1개)
11:39:23.204~.212   17~30번 closed  (14개)
11:39:23.285~24.205 32~45번 opened  (14개)
```

5분마다 evictor가 돌고, 커넥션은 정확히 10분을 살고 교체된다. 이게 12:59까지 한 번도 어긋나지 않고 반복됐다.

**두 관측 모두 사실이었다.** 개수는 15로 고정돼 있고, 그 15개의 실체는 10분마다 전부 바뀐다. 컨트롤러에서 `getNumIdle()`만 찍어서는 절대 보이지 않는 일이다. 폐기와 되채움이 같은 evictor 실행 안에서 끝나기 때문에, 어느 시점에 찍어도 15가 나온다.

가설이 틀린 지점은 commons-pool2의 폐기 판정에 있었다. 조건이 두 개다.

| 설정 | 조건 | minIdle |
| :--- | :--- | :--- |
| `softMinEvictableIdleTimeMillis` | 유휴 시간 초과 **그리고** idle > minIdle | 존중한다 |
| `minEvictableIdleTimeMillis` | 유휴 시간 초과 | **무시한다** |

내가 설정한 건 아래쪽이다. 이건 현재 idle이 몇 개든 시간만 넘기면 폐기한다. minIdle 하한을 뚫고 15개를 다 지우고, 그 직후 `ensureMinIdle`이 15개를 새로 채운다. 로그에서 close 14개가 먼저 몰아치고 70ms 뒤에 open 14개가 이어지는 순서가 그 증거다. 하나 지울 때마다 하나 채우는 게 아니라, 폐기 패스를 끝낸 뒤 부족분을 일괄 보충한다.

그리고 `softMinEvictableIdleTimeMillis`는 기본값이 -1이라 애초에 돌지 않는다. minIdle을 존중하는 쪽은 꺼져 있었고, 무시하는 쪽만 켜져 있었다.

### 14와 1로 갈리는 이유

로그에는 설명이 필요한 게 하나 더 있었다. 15개가 한 번에 움직이지 않고 14개와 1개로 나뉘어 5분씩 엇갈려 돈다.

로그 맨 앞에 답이 있었다. 11:24:20에 실제 요청이 하나 들어왔고, 그게 16번 커넥션을 썼다. 빌렸다 반납하면 그 커넥션의 **유휴 시계가 반납 시점으로 리셋된다.** 나머지 14개는 서버 시작 이후 계속 놀고 있었으니 시계가 그대로다.

그래서 14개는 11:29에, 16번은 5분 늦은 11:34에 10분을 채운다. 그리고 그 위상차가 그대로 상속된다. 11:29에 태어난 14개는 11:39에, 11:34에 태어난 1개는 11:44에. 요청 한 번이 만든 5분의 시차가 한 시간 반 동안 유지됐다.

## 그래서 어디까지 막히는가

관측 5가 처방을 바꿨다. 코어 15개도 10분마다 갈리므로, **거기 매달린 DB 링크도 10분마다 정리된다.** 방화벽 유휴 타임아웃이 30분이든 한 시간이든, 링크가 죽을 만큼 방치될 구간이 생기지 않는다.

풀 설정만으로 상당 부분이 막힌다. 다만 조건이 붙는다.

**경계 조건.** 이 방어는 `minEvictableIdleTimeMillis < 방화벽 유휴 타임아웃`이 성립할 때만 유효하다. 인프라 팀이 타임아웃 값을 바꾸면 우리 설정은 조용히 무력해진다. 값에 의존하는 방어라서, 그 값이 변한다는 통보를 받을 방법이 없다는 게 이 방식의 약점이다.

**사각지대.** 유휴 시계는 커넥션이 반납될 때 리셋된다. 16번 커넥션이 요청 한 번으로 5분을 벌었듯이, 커넥션이 로컬 쿼리만으로 꾸준히 바쁘면 그 커넥션은 폐기 대상이 되지 않는다. 그런데 링크 쪽은 로컬 쿼리 트래픽을 받지 못한다. **세션은 바쁜데 링크만 유휴인 상태**가 만들어지고, 여기는 evictor가 손대지 않는다.

이 경우 링크는 죽고, 다음 `@IRIS_DB` 호출에서 ORA-03150이 한 번 나고, 로컬 DB가 죽은 링크를 폐기한 뒤 다음 호출은 성공한다. 처음 우리가 겪은 그 패턴이다.

## 안 한 선택들

**HikariCP로 교체.** 이 문제의 정공법에 가장 가깝다. HikariCP에는 `maxLifetime`이 있고, 공식 문서가 "인프라의 커넥션 타임아웃보다 몇 초 짧게 잡으라"고 못 박는다. 우리가 evictor로 손수 만든 회전이 설계 기본값으로 들어가 있다. 하지만 Spring 4.3 / 폐쇄망 / 라이브러리를 수동으로 `WEB-INF/lib`에 넣는 환경에서 풀 교체는 이 문제 하나를 풀자고 감당할 변경이 아니다. 알고 안 했다.

**validationQuery를 링크 타는 쿼리로 변경.** `SELECT 1 FROM DUAL`이 링크를 검증하지 못하니, 검증 쿼리를 `@IRIS_DB`를 타게 만들면 링크의 생사를 직접 확인할 수 있다. 하지만 대여마다 원격 왕복이 붙고, 검증이 링크를 여닫으며 비용을 만든다. 문제를 막으려고 문제의 원인인 링크 사용을 늘리는 셈이라 접었다.

**`SQLNET.EXPIRE_TIME`.** 양쪽 DB의 `sqlnet.ora`에 keepalive를 걸면 방화벽이 링크를 유휴로 판정하지 못한다. 링크를 죽였다 살리는 대신 살려두는 방식이라 위의 사각지대까지 덮고, 방화벽 값에 의존하지도 않는다. 이건 안 한 선택이 아니라 **아직 못 한 선택**이다. DBA 협조와 변경 절차가 필요하고, 공기업 폐쇄망에서 그 절차는 짧지 않다. 앱 레벨에서 오늘 배포할 수 있는 것부터 걸어두고, 이건 병행해서 요청 중이다.

## 검증하지 못한 것

이 글의 손검증에는 명확한 경계가 있다.

로컬에서 재현하고 로그로 확인한 것은 **커넥션 풀 쪽**이다. 지연 초기화, 대여 시 검증, 두 풀의 합산, 10분 주기 교체, 14/1 위상차. 여기까지는 재현 가능하다.

**DB 링크가 방화벽에 끊기는 장면 자체는 재현하지 못했다.** 사내 폐쇄망 구성이고 원격 DB와 방화벽 정책은 내 손에 없다. 링크 부분은 에러 로그와 오라클 문서에 기댄 추론이고, "10분 회전이 실제로 ORA-03150 발생 빈도를 낮췄는가"는 운영에 올린 뒤 몇 주간 관찰해야 답이 나온다. 지금 시점에서는 아직 모른다.

## 정리

- ORA-03150은 애플리케이션 계층의 예외가 아니다. `ORA-02063 ... from IRIS_DB`가 발생 지점을 알려준다. 무대는 로컬 DB와 원격 DB 사이다.
- DB 링크 세션은 로컬 세션에 매달린다. 커넥션 풀이 로컬 세션을 오래 재사용하는 만큼, 링크도 오래 방치된다. 방화벽이나 원격 DB가 그 유휴 링크를 끊고, 로컬 DB는 통보받지 못한다.
- `minIdle`은 바닥이고 `maxIdle`은 천장이다. 둘 다 idle만 규제하며 active와 무관하다. 기동 시 생성은 `initialSize`, 대기 시간은 `maxWaitMillis`가 맡는다.
- `timeBetweenEvictionRunsMillis`가 없으면 evictor 스레드가 뜨지 않고, 유휴 폐기·유휴 검증·minIdle 되채움이 전부 죽는다.
- `minEvictableIdleTimeMillis`는 minIdle을 무시하고 폐기한다. minIdle을 존중하는 쪽은 `softMinEvictableIdleTimeMillis`이고 기본값은 비활성이다.
- 그 결과 무트래픽 상태에서 idle 개수는 고정된 채 커넥션 실체만 주기적으로 교체된다. `getNumIdle()` 한 번으로는 관측되지 않는다.
- `testOnBorrow` / `testWhileIdle`의 검증 쿼리는 로컬 커넥션까지만 확인한다. DB 링크의 생사는 검증 범위 밖이다.
- 커넥션 번호는 생성 누적 순번이다. 현재 개수가 아니고, 여러 풀이 하나의 카운터를 공유한다.

스택트레이스 한 장에서 시작했다. 고칠 코드를 찾다가, 고칠 코드가 없다는 게 답이라는 걸 알았다. 그리고 설정 문서를 읽고 세운 가설이 로그 앞에서 한 번 뒤집혔다. 숫자가 그대로였던 건 아무 일도 없어서가 아니라, 매번 같은 자리에 다른 커넥션이 서 있었기 때문이었다.
