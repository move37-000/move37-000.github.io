## 과거의 생각과 선택
권한별 메뉴 관리 기능을 만들면서 회사 코드 구조를 정리한 글이 있다. 그때의 난 아래와 같이 생각하고 있었다.

> **이건 패키지 분리가 아니라 화면 복제다.** 화면 메뉴는 요구사항으로 수시로 재편된다. "개선사항을 별도 최상위 메뉴로 빼주세요" 한 마디에 `import` 경로 전부가 바뀐다.
> 
> `Netflix`, `Naver`, `Kakao` 같은 테크 기업 오픈소스를 보면 전부 **도메인 기반 평평한 구조**다.
>
> [당연했던 것들에 생각이 들어간다면](https://move37-000.github.io/posts/backend-architecture-3/)

4개월이 지났고, 새로운 요구사항이 생겨 업무 화면을 만들기 전에 이전에 패키지를 어떻게 나눴는지 다시 확인해봤다. 내가 만든걸 다시 들여다봤지만, 지금의 생각은 그때와 달라졌다.

> 이미 작성한 글은 그 시점의 기록이기에 수정하지 않으며, 새로운 글(이 글과 같은 글)에서 이어간다.

## 기준점에서 벗어난 비교 대상
오픈소스 라이브러리에는 **애초에 화면이 없다.**

메뉴 트리가 없는 코드베이스가 메뉴 기준으로 안 나뉜 건 당연하다. 이 기준점을 고려하지 못한 채 회사 프로젝트 코드베이스와 비교해버리니 자연스레 이전 글의 결론인 **메뉴 기준이 나쁘다**가 나와버렸다.

내가 비교했어야 할 대상들은 사내 어드민, ERP, 그룹웨어, 운영 시스템처럼 화면이 유일한 진입점이고, 담당자가 몇 년 단위로 바뀌며, 요구사항이 메뉴 단위로 들어오는 시스템이었다.

비교 대상부터 잘못 골라놓고 그 비교에서 나온 결과를 근거로 결론을 만들어내버렸다. 결국 내가 보고 싶은 결과만 남은 셈이다.

## 바라보는 시각마저 달랐다
4월 글에서 나는 권한별 메뉴 관리를 `menu`와 `menuauth`로 나누며 이유를 아래와 같이 생각했다.

> **주어가 다른 도메인이기 때문이다.** 각 업무 화면에서 동일한 쿼리가 발생했다. 하지만 그렇다 해도, 분리를 하는 방향으로 진행했다.

`menu`와 `menuauth`는 메뉴 트리에서도 별개 메뉴라, 메뉴 구조를 따라가도 어차피 나뉜다. 결과만 보면 어느 기준으로 나눴는지 알 수 없다.

그런데 그때의 내가 실제로 고민하고 있던 생각은 "메뉴 조회 쿼리가 똑같은데 합쳐야 하나"였고, 분리를 한 이유로 **메뉴가 다르니까가 아닌** "주어가 다른 도메인"를 생각해냈다.

그때의 나는 메뉴와 무관한 기준을 하나 잡아두면서, 같은 글에서 이 코드베이스를 "화면 복제"라고 생각했다. 코드를 짤 때는 도메인을 기준으로 나눴으면서, 코드를 해석할 때는 화면을 기준으로 바라보고 있었던 셈이다.

## 지금 구조
```
kr.co.company
├── common
│   ├── dto
│   ├── access
│   ├── popupa
│   └── popupb
│
├── system                    // 레벨1
│   └── management            // 레벨2
│       ├── menu              // 레벨3
│       │   ├── controller
│       │   ├── dto
│       │   ├── repository
│       │   └── service
│       └── menuauth          // 레벨3
│           └── ...
│
└── safety                    // 레벨1
    └── task                  // 레벨2 — 여기가 종단
        ├── controller
        ├── dto
        ├── repository
        └── service
 
com.company
├── config
└── batch
```

`system/management`와 `safety/task` 는 둘 다 레벨2인데 한쪽은 아래에 레벨3이 있고, 한쪽은 없다.

메뉴 구조를 그대로 따라갔다면 레벨3이 존재하기 때문에 `safety/task/task` 가 되었을 것이다.

이유는 단순하다. 상위 업무에 속한 업무가 단수냐 복수냐의 차이다. `management` 아래에는 업무가 둘이라 나뉘었고, `task` 아래에는 하나뿐이라 나뉘지 않았다. 앞으로 `task`에 속한 업무가 추가되면 그때 `management`처럼 분기한다.

메뉴를 닮았지만 메뉴를 따라간 게 아니다. 닮은 이유는 대부분의 경우 두 기준의 결과가 우연히 일치하기 때문이고, `task`는 일치하지 않은 지점이다.

## 그래서 기준은 두 개다

정리하면 이렇다.

| | 무엇을 정하나 |
| :--- | :--- |
| 메뉴 뎁스 | 패키지의 **위치** |
| 응집도(업무 단복수) | 종단의 **분할** |

메뉴 뎁스는 어디에 놓을지를 정할 뿐 몇 단계로 팔지는 정하지 않는다. 뎁스 3단계는 목표가 아니라 하위 업무가 복수일 때 나오는 결과다.

## `common`은 왜 축 밖에 있나

`common`은 어느 메뉴 레벨에도 속하지 않는다. `dto` 같은 타입, 외부에서 사이트로 진입할 때 타는 로직, 여러 업무 화면에서 공통으로 띄우는 조회 전용 팝업들이 들어 있다.

기준은 하나다. **특정 화면에 귀속되지 않은 것.**

팝업은 화면이지만 반드시 부모 창에서 띄우고 등록·수정·삭제가 없다. 독립적으로 진입할 수 없으니 어느 업무 패키지에도 귀속되지 않는다. 진입 로직은 화면에 도달하기 이전 단계고, `dto`는 애초에 화면과 무관하다.

화면 축으로 나눌 수 없는 것들을 화면 축에 억지로 걸 수는 없다. 그래서 축 밖으로 뺐다.

## 예상했던 비용은 나오지 않았다

메뉴 기준 구조의 대표적인 단점은 중복이 구조적으로 유도된다는 것이다. 두 메뉴가 비슷한 로직을 쓸 때 공유할 자리가 없으니 복붙하거나 `common`으로 밀어 넣게 된다. 그 결과 `common`이 갈 곳 없는 코드의 잔여 저장소가 된다.

이번에 `common`을 열어봤다. 그런 코드는 나오지 않았다. 안에 있는 것들은 전부 "특정 화면에 귀속되지 않음"이라는 한 기준으로 묶여 있었다.

기대에 못 미친 결과를 숨기지 않는 규칙은 유리한 결과에도 똑같이 적용된다. 예상한 비용이 관측되지 않았으면 안 나왔다고 쓴다. 다만 이건 이 프로젝트의 규모와 업무 성격에서 그랬다는 것이지, 메뉴 기준 구조가 그 단점을 갖지 않는다는 뜻은 아니다.

## 루트를 나눈 기준은 또 달랐다

이 프로젝트에는 최상위 패키지 루트가 둘이다. 업무와 `common`은 한쪽, 스프링 설정과 배치는 다른 쪽에 있다.

원래는 하나였다. 입사하고 투입됐을 때 이 프로젝트는 루트 하나 아래에 설정도, 배치도, 화면 업무도 전부 들어 있었다. 3년차에 이 프로젝트를 혼자 맡게 되면서 둘로 갈랐다.

그때 근거는 이랬다. **어떤 건 스프링 설정이나 배치 작업이고 어떤 건 눈에 보이는 화면 업무인데 한 경로에서 갈라지니, 소스 보기가 복잡할 것 같았다.**

기준으로서 소박하다. 그래서 4월 글에도 안 썼다. 오픈소스나 아키텍처 정석 쪽이 더 그럴듯해 보였다.

그런데 지금 보면 이게 이 환경에서 가장 정확한 기준이었다. 공공 SI 유지보수에서 하루 업무의 대부분은 "이 화면 어디 있지"다. 로직을 재설계할 일은 거의 없다. 탐색 비용이 1순위 비용인 환경에서 "찾기 쉽게"는 소박한 게 아니라 핵심이다.

그리고 같은 기준이 메뉴 뎁스를 유지하기로 한 판단의 근거이기도 하다. 요구사항이 메뉴 단위로 들어오고 권한도 메뉴 단위로 걸리는데 코드만 다른 축으로 나뉘어 있으면 매번 번역이 필요하다.

한 가지는 분명히 해둔다. 루트를 나눌 때 나는 "설정과 화면은 실행을 시작시키는 주체가 다르다" 같은 생각을 하지 않았다. 그냥 섞여 있는 게 보기 불편했다. 지금 와서 보니 그렇게 읽힌다는 것이지, 그 축을 의도하고 설계한 게 아니다.

## 남은 문제 — 두 구조가 공존한다

지금 내가 만든 업무 패키지의 종단 안쪽은 두 종류다.

```
controller / service / serviceimpl / dao      // 기존
controller / dto / repository / service       // 이후
```

구현체가 하나뿐인 `service` 인터페이스를 없앴고, `dao`를 역할에 맞게 `repository`로 불렀고, 입출력 타입을 `dto`로 분리했다. 방향은 한쪽이다.

문제는 둘이 공존한다는 게 아니라, **둘 중 뭐가 방향인지 코드가 말해주지 않는다는 것**이다. 인수인계받는 사람은 "왜 두 개지, 뭐가 맞는 거지"부터 시작해야 한다. 주석은 클래스가 뭘 하는지는 설명해도 이건 설명하지 못한다.

그래서 한 줄을 남기기로 했다.

> `repository`가 있으면 신규 구조, `dao`가 있으면 기존 구조. 신규 개발은 신규 구조를 따른다.

기존 화면을 구조 통일 목적만으로 건드리지는 않는다. 테스트 환경이 없는 폐쇄망에서 동작하는 화면을 만지는 건 순수 리스크다. 기능 수정이 들어가는 화면만 그 김에 옮긴다.

## 나가며

이 글은 4월 글을 뒤집는 글이지만, 그때 판단이 전부 틀렸던 건 아니다. 틀린 건 근거였다. 화면이 없는 코드베이스를 근거로 화면이 전부인 코드베이스를 평가했다.

판단 기준을 스스로 언어화하지 않으면 평가할 자가 없으니 외부 기준을 빌려오게 된다. 빌려온 기준은 이쪽 환경을 모르니 안 맞고, 안 맞으면 내 코드가 틀린 것처럼 보인다. 실제로는 내가 만든 축이 3년째 일관되게 굴러가고 있었는데도 그랬다.

한 가지 덧붙인다. 이 글의 정리는 대화를 통해 나왔고, 그 과정에서 결론이 세 번 뒤집혔다. 팝업을 구조의 빈틈이라고 봤다가 부모 창에서만 열린다는 걸 확인하고 철회했고, 루트 분리를 설계된 축이라고 봤다가 당시 근거가 "보기 복잡할 것 같아서"였다는 걸 떠올리고 내려놨다. 최종 정리만 써놓으면 처음부터 알고 있었던 것처럼 읽힌다. 그건 사실이 아니다.

다음 글에서 회수할 것 두 가지를 미리 적어둔다. 도움이 된 규칙은 "완료된 글은 소급 수정하지 않고 다음 글에서 이어받는다"였다. 4월 글을 고치려 들었다면 근거가 틀렸다는 사실 자체가 사라졌을 것이다. 안 맞았던 규칙은 아직 모르겠다 — 이 글을 쓰는 동안에는 걸리는 게 없었는데, 매번 다 잘 맞았다는 건 보통 진지하게 시험하지 않았다는 뜻이라 일단 의심으로 남겨둔다.은 소급 수정하지 않고 다음 글에서 이어받는다"였다. 4월 글을 고치려 들었다면 근거가 틀렸다는 사실 자체가 사라졌을 것이다. 안 맞았던 규칙은 아직 모르겠다 — 이 글을 쓰는 동안에는 걸리는 게 없었는데, 매번 다 잘 맞았다는 건 보통 진지하게 시험하지 않았다는 뜻이라 일단 의심으로 남겨둔다.
